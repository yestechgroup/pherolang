# Documentation strategy

The decision record for this system is
[ADR 0011](../adr/0011-documentation-quality-standard.md). This page states the
philosophy the rest of the governance set implements.

## What we are optimizing for

Phero Lang is becoming a modelling ecosystem: several related languages, each
with its own syntax, concepts, and role. The documentation problem is not
"write more pages". It is:

> **Consistency without forcing every language to explain itself the same way.**

A reader who learns `.mox` should recognize how a `.ddd` page is organized.
A reader who knows nothing should be able to find the language they need from
the problem they have. Neither goal is served by a pile of well-intentioned
prose.

## Principles

1. **One architecture across all languages.** The same page types, the same
   metadata, the same editorial standard; the same navigation rules.
2. **Diátaxis decides what kind of page this is.** Tutorials teach, how-tos
   solve, concepts explain, references state. A page has exactly one type, and
   the type determines its section structure.
3. **One authoritative page per concept.** Everything else links to it. Duplicate
   explanations drift and then contradict each other.
4. **User documentation and engineering documentation are separate products.**
   Implementation detail is preserved, owned, and linked — not interleaved with
   the language a user is trying to learn.
5. **Examples are executable.** A documentation change that breaks an example
   fails CI, exactly as a code change that breaks a test does.
6. **Standards provenance is explicit.** "Aligned with OMG IFML 1.0" is a claim
   with a page behind it, not a phrase used for credibility.
7. **Maturity is a fact, not a hope.** Feature status and documentation status
   are separate fields and are never optimistic.
8. **Plain English, precise technical language, one vocabulary.** The glossary
   is the vocabulary authority; `docs/NAMING.md` owns spelling.
9. **Documentation changes are part of language development.** A behavior change
   and its documentation change land together.
10. **Every rule is enforced or it is not a rule.** `[CI]` gates and `[REVIEW]`
    checklist rows, never "we should try to".

## What this system is not

- **Not a rewrite programme.** The governance and the gates come first. Pages
  migrate when their subject is next touched or when the language's turn in the
  rollout comes.
- **Not a second source of truth.** Prose stays in this repository; the site
  projects it. Artifacts and examples stay generated by the toolchain.
- **Not a ban on technical depth.** Engineering reference pages are expected to
  be precise and complete. They are simply not the front door.
- **Not a template for its own sake.** A section that has nothing to say is
  removed from the model, not filled with filler.

## The quality bar

A page is ready when:

- a reader can state, after the first paragraph, whether the page is for them;
- every term in it is defined here or linked to its authority;
- every example compiles, and every invalid example names its expected
  diagnostic;
- it cannot be mistaken for a description of a different Diátaxis type;
- it has exactly one home in the routing table;
- and it contains no sentence that only a contributor could act on.

This is the bar the five `.mox` exemplar pages are held to.

## Rollout

1. Governance set, templates, and the `.mox` exemplars — landed.
2. The documentation gate and the pull-request checklist — landed
   (`pherolang docs lint`, CI step 3/8).
3. `.ddd` redistribution pilot: the worst current mixture of user and
   engineering material, and the best test of the architecture — landed
   (eleven pages; `docs/DDD.md` remains the engineering contract and is linked
   from the Guide).
4. `.ifml` pilot plus its conformance page, to prove the architecture fits a
   standards-derived language — landed (ten pages, including the OMG
   conformance page).
5. `.dmn` pilot plus its conformance page, with the `.mox` reference depth that
   gives both a type authority — landed (twelve pages across the two trees).
6. Remaining languages, one at a time, against the same checklist.

The pilot order is deliberate. `.mox` comes first because it is the entry
language; `.ddd` is the first *rewrite* because it contains the broadest
mixture of concepts, formal semantics, and implementation detail. `.ifml`
follows because its conceptual structure is different enough to falsify the
architecture if it is wrong.
