# Compiler-backed syntax highlighting

Phero Lang source is highlighted by the compiler, not by a hand-written
grammar. One language model — the taxonomy, the nine-surface registry, and
the engine in the `phero-highlight` crate — drives every consumer: the
`pherolang highlight` JSON/HTML output, the generated TextMate grammars and
language configurations (`pherolang grammar`), the static sites (SH4), LSP
semantic tokens and hover (SH6), and the static hover reference panels (SH7).

The parser modules are the grammar authority. This document is the
**highlighting contract**: the vocabulary, the spans, the engine guarantees,
and the wire/HTML formats. When prose here and a lexer or parser disagree,
the lexer/parser wins; change both in the same commit.

## Purpose

- **One model, every renderer.** The static site, the generated TextMate
  grammar, and LSP semantic tokens must all derive from the same span
  stream. There is no second taxonomy and no second grammar.
- **The compiler is the source of truth.** Keywords, contextual words,
  literals, built-in types, declarations, and references come from the
  lexers and ASTs in `phero-syntax` / `phero-ifml`. A site-side keyword list
  would be a second source of truth and is forbidden.
- **Never a second parser.** `phero-highlight` consumes tokens and ASTs; it
  does not lex, parse, or re-implement a grammar.
- **Always useful, never fatal.** Fragments, docs fences, and broken source
  receive best-effort lexical highlighting and an explicit `degraded` flag
  instead of an error page.
- **Deterministic and offline.** The same input produces byte-identical
  output; the CLI touches only its inputs and outputs, and never the
  network.

## Architecture

```text
phero-syntax (logos lexers + ASTs) ─┐
                                    ├─> phero-highlight
phero-ifml   (logos lexer + AST)  ──┘   taxonomy + registry + engine
                                        JSON / HTML renderers
                                             │
                        ┌────────────────────┼────────────────────┐
                        ▼                    ▼                    ▼
                pherolang highlight     pherolang grammar       LSP (SH6)
                 JSON / HTML           TextMate grammars +      semantic tokens
                                        language config (SH5)
```

- `phero-syntax` owns the `.mox` family lexer, parser, contextual word
  tables, and byte spans. `phero-ifml` owns the same for `.ifml`.
- `phero-highlight` owns `HighlightClass`, `HighlightModifier`,
  `HighlightSpan`, `HighlightOptions`/`HighlightMode`, `HighlightResult`,
  the nine-surface registry, the classifier, and the JSON/HTML renderers.
  It depends on the two front-end crates; they never depend on it.
- `phero-cli` hosts the command. Its output is the contract the site and
  editor tooling consume — they never link the Rust AST directly.
- The registry is the only place a consumer asks *what words does this
  surface know?* or *what does this token mean?*.

## Class taxonomy

`HighlightClass` and `HighlightModifier` are `#[non_exhaustive]`: a new
member is a deliberate additive change. A consumer that wants forward
compatibility should skip a span whose class it does not know; the reference
Rust model rejects an unknown class rather than guessing at a colour. The
`formatVersion` gate is the primary compatibility boundary. Class wire
spellings are **lowercase** (`keyword`, not `Keyword` or `KEYWORD`); HTML
classes prefix them with `hl-`.

| Wire spelling | Rust variant | Meaning |
|---|---|---|
| `keyword` | `Keyword` | A real lexer keyword, or a contextual word in the grammar position that makes it special |
| `type` | `Type` | A declared type name, a type reference, or a built-in type (built-ins also carry `defaultLibrary`) |
| `function` | `Function` | A function, operation, service operation, action, command, or capability name |
| `namespace` | `Namespace` | A package, application, module, import alias, or model-level namespace |
| `variable` | `Variable` | An ordinary value binding or reference (for example a `.ddd` statement binding) |
| `parameter` | `Parameter` | An operation/service parameter, `.ifml` param, command argument or option, or task input |
| `property` | `Property` | A feature, attribute, field, property assignment, or setting-path member |
| `string` | `String` | A string literal; escapes inside it are separate `escape` spans |
| `number` | `Number` | An integer or floating-point literal |
| `comment` | `Comment` | A line or block comment; documentation comments also carry `documentation` |
| `operator` | `Operator` | An expression or structural operator (`=`, `->`, `==`, `->`, …) |
| `punctuation` | `Punctuation` | A structural delimiter (braces, brackets, parentheses, commas, semicolons, colons, dots) |
| `annotation` | `Annotation` | An annotation name, decorator word, design flag, or their use positions |
| `constant` | `Constant` | A boolean, enum member, vocabulary word, ranking literal, or other closed-set literal |
| `escape` | `Escape` | An escape sequence inside a string literal; a surface that lexes the literal atomically reports it as part of `string` |
| `error` | `Error` | An invalid or unrecognized region; still bounded and non-overlapping |

Classes track the LSP semantic-token vocabulary closely so the LSP adapter
is a mapping, not a second taxonomy
([LSP semantic tokens](#lsp-semantic-tokens)); `punctuation` and `error` have
no standard LSP type and are omitted there. A surface that has no construct
for a class simply never emits it; that is not an error.

## Modifiers

`HighlightModifier` is a set on each span. Wire spellings are lower
camelCase (`defaultLibrary`); HTML spells them kebab-case
(`hl-default-library`). The array is always present and is serialized in the
canonical order below, without duplicates.

| Wire spelling | Rust variant | Meaning |
|---|---|---|
| `declaration` | `Declaration` | The identifier introduces a declaration |
| `definition` | `Definition` | The span is a symbol's definition site (LSP `definition` modifier) |
| `readonly` | `Readonly` | The declaration or binding is immutable (`readonly`, a `let` binding) |
| `deprecated` | `Deprecated` | The symbol is deprecated |
| `documentation` | `Documentation` | A documentation-carrying comment or node |
| `defaultLibrary` | `DefaultLibrary` | A built-in type or otherwise library-defined symbol |

Modifiers refine a class; they never replace it. An unknown modifier from a
newer format version is treated like an unknown class (skipped by a
forward-compatible consumer, rejected by the reference Rust model).

## The nine-surface registry

Surface ids are the file extensions and the canonical `--surface` values.
They mirror `phero_parser::Surface` — the workspace's one surface identity,
re-exported by the driver as `SurfaceKind` — and are drift-tested against it;
the registry is the highlighter's dispatch key, not a second extension map.

| Id | Extension | Lexer family | Language documentation |
|---|---|---|---|
| `mox` | `.mox` | `phero-syntax` (logos lexer + chumsky AST) | [LANGUAGE.md](LANGUAGE.md) |
| `ifml` | `.ifml` | `phero-ifml` (logos lexer + chumsky AST) | [IFML.md](IFML.md) |
| `ddd` | `.ddd` | `phero-syntax` | [DDD.md](DDD.md) |
| `actor` | `.actor` | `phero-syntax` | [LANGUAGE.md](LANGUAGE.md#actor-policy-files-actor) |
| `evt` | `.evt` | `phero-syntax` | [EVENTS.md](EVENTS.md) |
| `deploy` | `.deploy` | `phero-syntax` | [DEPLOY.md](DEPLOY.md) |
| `uc` | `.uc` | `phero-syntax` | [USECASES.md](USECASES.md) |
| `cmmn` | `.cmmn` | `phero-syntax` | [CMMN.md](CMMN.md) |
| `dmn` | `.dmn` | `phero-syntax` | [DMN.md](DMN.md) |

Each registry entry records the id, extension, display name, aliases, lexer
entry point, token/word classification, declaration forms, and the
documentation link. The keyword, contextual, and literal tables are
borrowed from `phero_syntax::words` / `phero_ifml::words`; built-in type
names come from `phero_ifml::words::TYPE_REFS` for `.ifml` and the shared
built-in list for the other surfaces. No table is copied into the
highlighter. Ids and extensions are canonical; aliases (`domain`, `flow`,
`design`, …) are editor convenience spellings, never a second taxonomy. A
surface with no construct for a class records that explicitly; a silent
omission is a bug.

Every surface is covered by the checked corpus and by at least one
documentation fence. A small `.actor` policy, for example, uses the same
stream as the domain it governs:

```actor
import "support.mox"

actors Support {
    actor Agent
    capability ReadTicket on Ticket

    grant Agent {
        permit ReadTicket
    }
}
```

## Source-of-truth rules

The grammar vocabulary has three owners, and no consumer keeps a fourth
copy. Built-in type names are the one registry-owned list.

### Real lexer keywords

For the `phero-syntax` family, the logos `#[token]` / `#[regex]`
declarations in `crates/phero-syntax/src/lexer.rs` are the lexical source.
`phero_syntax::words` exposes the derived tables — `KEYWORDS`,
`MOX_KEYWORDS`, `ACTOR_KEYWORDS`, `DDD_KEYWORDS`, `EVT_KEYWORDS`,
`DEPLOY_KEYWORDS`, `UC_KEYWORDS`, `CMMN_KEYWORDS`, `DMN_KEYWORDS`, and the
literal tables — and its tests fail when a table and the lexer drift apart.
The highlighter classifies through the registry; it never re-types the list.

A word is not a keyword on every surface. `container` is a real `.mox`
lexer keyword but an ordinary word in `.deploy` value position; `.deploy`
has only `import` as a real keyword, while `.ddd` has `import`,
`capability`, `when`, and `version`.

### Contextual words

Contextual words are ordinary identifiers that are special only in a grammar
position. Their authority is the parser module and the per-surface word
table in `phero-syntax` (`crates/phero-syntax/src/{ddd,deploy,dmn,usecases,
cmmn}.rs`), exposed through `phero_syntax::words` as the
`*_CONTEXTUAL` / literal tables. `id` and `readonly` are contextual feature
modifiers, not keywords; `schema` and `sigil` are contextual only after
`import`; `to` is contextual on a delegation line.

### `.ifml` curated words

`.ifml` has **no keyword tokens**: every word is an identifier and is
special only in the position the parser dispatches on. Its grammar
vocabulary is curated in `phero_ifml::words` (`STRUCTURAL_WORDS`,
`TYPE_REFS`, `BOOLEANS`) and kept aligned with the parser EBNF by tests.
The registry classifies `STRUCTURAL_WORDS` as `keyword` — they are grammar
words, not reserved tokens — and `TYPE_REFS` as `type` with
`defaultLibrary`. The closed data vocabularies (`button`, `list`, `text`, …)
remain owned by `phero-ir`; they are property values, not grammar words, and
are not highlighted as keywords.

### Grammar authority

- `.mox` family EBNF: [`crates/phero-syntax/src/parser/mod.rs`](../crates/phero-syntax/src/parser/mod.rs)
- `.ifml` EBNF: [`crates/phero-ifml/src/parser/mod.rs`](../crates/phero-ifml/src/parser/mod.rs)
- Expressions: [EXPRESSIONS.md](EXPRESSIONS.md)

### Adding a keyword

1. Change the owner: a logos `#[token]` for a real keyword, or the parser's
   contextual table for a contextual word.
2. Update the matching `phero_syntax::words` / `phero_ifml::words` table and
   its parser spot-check test. `every_parser_table_word_appears_in_the_registry`
   fails by surface name if the registry misses it.
3. Add or extend a corpus case under `tests/highlight/corpus/` — a real
   grammar position **and** an ordinary position for a contextual word — and
   regenerate `tests/highlight/summary/corpus.json` plus any exact-span
   golden:
   ```sh
   PHERO_UPDATE_FIXTURES=1 cargo test -p phero-highlight --test corpus
   ```
4. Regenerate the editor grammars (the word tables are the only source):
   ```sh
   cargo run -q -p phero-cli -- grammar --out site/packages/highlighting
   ```
5. Add or extend a docs fence. `tests/highlight/summary/docs-fences.json`
   and the site gate both fail when a fence is missing or changed without
   regeneration. The registry and the highlighter need no edit for a word —
   that is the point.

A new token **variant** is the exception: it joins the registry's exhaustive
classifier in the same commit, or the build fails.

### Adding a surface

1. Add the `Surface` arm and `Surface::ALL` entry in `phero_parser` (the one
   compiler table; the driver re-exports it as `SurfaceKind`).
2. Add the lexer/parser and its word tables in the owning front-end crate.
3. Add one registry row (id, extension, lexer family, docs link).
4. Add a corpus directory under `tests/highlight/corpus/<id>/` with `valid`,
   `truncated`, and `parse-error` cases. `every_surface_has_a_corpus_case`
   fails by surface name otherwise.
5. Add a docs fence for the surface. `docs_fence_summary_covers_every_phero_fence`
   names the surface that has no documentation example.
6. Add the site row in `site/scripts/surfaces.mjs`, a `/languages/<id>/`
   page, and a `site/packages/highlighting/excerpts.json` entry; the site
   coverage and highlighting gates fail otherwise. Regenerate:
   ```sh
   PHERO_UPDATE_FIXTURES=1 cargo test -p phero-highlight --test corpus
   cargo run -q -p phero-cli -- grammar --out site/packages/highlighting
   node site/scripts/sync-model.mjs
   node site/scripts/sync-highlight.mjs
   ```
7. Extend the drift tests: every surface must have a registry entry, a
   corpus case, a grammar/configuration, and no contextual word may leak
   between surfaces.

## Span contract

The core is byte-based and never panics on malformed input.

- A span is `{ start, end }` with **byte offsets** and a **half-open**
  range `[start, end)`. `start < end`; empty spans are never emitted.
- Spans are sorted by `start`, non-overlapping, and bounded by
  `0..=source.len()`. Every offset is a UTF-8 boundary because it comes
  from a lexer or parser span.
- Whitespace and other unclassified gaps are **implicit**: they are not
  emitted and are reconstructed from the source between spans. The v1 wire
  format never emits a neutral/whitespace span.
- Comments are atomic: a comment gets exactly one span and no semantic
  span may split it. A string literal is lexically segmented into `string`
  pieces plus `escape` sub-spans for each `\\.` sequence; no semantic span
  may split either region. In `.ifml`, a string that names a declaration or
  reference is a semantic span over the **whole literal**, quotes included;
  it replaces the lexical string/escape spans rather than overlapping them.
- Parser spans override lexical identifier/type guesses over the same
  range. Adjacent spans with the same class and modifier set are merged.
- `sourceHash` and all spans refer to the exact bytes supplied. No line
  ending is normalized and no text is rewritten.
- UTF-16 is a boundary concern only: the LSP adapter converts once
  (`to_utf16`) when it speaks LSP. The CLI and HTML renderers stay in
  bytes and slice the source.

Invariants are enforced by tests: sorted, non-overlapping, in bounds, no
empty spans, no semantic split of a comment/string, and no span outside the
source.

## Engine contract

```rust
highlight(source: &str, surface: Surface, options: HighlightOptions) -> HighlightResult
```

`HighlightResult` carries `spans`, `degraded`, and `diagnostics` (the last
for LSP/tests; the CLI does not print them as errors).

### Strict and lenient

- **Strict** is the default for files and directories. It runs the surface's
  parser, uses the recovered AST (partial or complete), records every parser
  and lexical diagnostic, and sets `degraded = true` when the source did not
  parse cleanly. It still returns a result — strictness never changes the
  never-fail guarantee.
- **Lenient** is the default for stdin and docs fences. It runs the same
  parser and the same recovered-AST walk, but suppresses the diagnostics and
  still sets `degraded` truthfully. It never fails and never turns a parse
  error into an error page.
- A **degraded** result is a successful result: exit code 0 and a valid
  artifact (JSON carries `"degraded": true`; HTML still renders the lexical
  spans). An empty source is not degraded; it has no spans.
- `degraded` is truthful. Intentional lexical regions (below) do not set it;
  a missing or partial semantic pass does.

### One lex, one parse

The engine calls the surface's existing lexer and parser exactly once per
input. It must not reparse per token, allocate a second copy of the source,
or introduce a second grammar. `.mox` uses `lex_with_comments_lossy`
(comments are part of the span stream and invalid regions never abort the
scan); `.ifml` uses `parse_ifml_syntax_recovering` (the same parser the
compiler uses, without import or domain resolution), never a new parser.

### Semantic coverage

The semantic pass walks the AST and classifies:

- declaration names (`class`, `enum`, `actor`, `capability`, `service`,
  `repository`, `event`, `channel`, `subscription`, `case`, `stage`, `task`,
  `decision`, `decision_model`, `view`, `component`, `action`, `usecase`,
  `application`, `module`, `profile`, `deployment`, …)
- type references, enum members, namespaces, packages, and import aliases
- operation/service names, parameters, features, fields, and task inputs
- annotations and their arguments where spans exist
- contextual keywords the parser recognized (`.ddd` `service`, `.dmn`
  `logic`, `.uc` `realizes`, `.ifml` `view`/`type`, …)

### Intentionally lexical nodes

These are lexical by design in this slice and are documented, not guessed:

- `.ddd` `expr` and `rust` bodies (the driver type-checks/executes them; the
  highlighter emits their raw text lexically)
- expression subnodes beyond declarations and references (a later
  refinement; SH2 prioritized declarations, references, types, functions,
  namespaces, and contextual keywords)
- comments, string literals, numbers, and error regions, which are lexical
  classes by definition

Leaving a node lexical is not a parse failure and does not set `degraded`.

### Resolution order

1. Comments and string interiors are immutable.
2. Parser declaration/reference spans override lexical guesses.
3. Adjacent equal spans merge.
4. Everything else falls back to the lexical class from the registry.

## LSP semantic tokens

`phero-lsp` answers `textDocument/semanticTokens/full` from the same
`phero_highlight::highlight` result the CLI renders: an open document of any
of the nine surfaces is highlighted once per version and its spans are
converted for the protocol. There is no separate grammar, span stream, or
editor-side classification, so lexical classes (comments, strings, numbers,
keywords, operators) and the semantic
declaration/reference/type/function/namespace classes all arrive through the
one span stream.

### Legend derivation

The legend is **derived, never hand-listed**. `phero_highlight::lsp_token_type`
maps each `HighlightClass` to its standard LSP token type (returning `None`
where none exists), and `phero_highlight::lsp_modifier` is the identity
spelling of each `HighlightModifier`; both are public API exercised against
the taxonomy, so the legend and the span vocabulary cannot drift apart.

| Legend token types (stable order, 13) | From `lsp_token_type` |
|---|---|
| `keyword` `type` `function` `namespace` `variable` `parameter` `property` `string` `number` `comment` `operator` `decorator` `enumMember` | `annotation` → `decorator`, `constant` → `enumMember`, `string` and `escape` → `string` |

| Legend modifiers (stable order, 6) | From `lsp_modifier` |
|---|---|
| `declaration` `definition` `readonly` `deprecated` `documentation` `defaultLibrary` | the span's modifier set, in canonical order |

**Standard-only.** The server advertises no custom token type; a legend a
standard client cannot render is not worth negotiating. `punctuation` and
`error` have no standard LSP type, so `lsp_token_type` returns `None` and
those spans are **omitted by decision** — punctuation is the editor grammar's
job (SH5), and lexical errors are reported as diagnostics, not coloured
tokens. Every other class maps to exactly one type.

### Encoding and scope

- **One conversion.** The adapter calls `to_utf16` once over the engine's
  byte spans; every later calculation is in UTF-16 code units, the protocol's
  unit. The engine's byte spans stay the source of truth.
- **Split at line boundaries.** An LSP token cannot span lines, so a
  multi-line span (a block comment, a string) becomes one token per line,
  each bounded by that line's content.
- **Delta encoding.** Tokens are emitted in document order as `deltaLine`,
  `deltaStart` (relative to the previous token when `deltaLine` is `0`, else
  the token's start column), `length`, `tokenType` (its legend index), and
  `tokenModifiers` (a bit set in legend order). An empty source returns an
  empty `data` array.
- **Full only.** This slice implements `textDocument/semanticTokens/full`
  only — no range request and no delta. The server declares exactly that
  capability; range/delta are a later additive step.
- **Per-version cache.** The token vector is cached per document and document
  version, so a repeated request or a version-bumping no-op change does no
  highlighting work; a new version invalidates the entry.
- **Parse-only for `.ifml`.** Every surface goes through its own registry
  entry; `.ifml` uses the parse-only path (`parse_ifml_syntax_recovering`), so
  tokens need no domain union or import bundle and a flow highlights while
  its imports or bindings are unresolved.
- **Never fatal.** A malformed, partial, or fragment document yields the
  lexical spans the engine could recover. The adapter never panics, never
  fails the request, and never emits a token outside the document's bounds.

## JSON wire format (v1)

The JSON artifact is the contract. It is a versioned, deterministic,
camelCase document with no source text, paths, timestamps, or
environment-specific data. For the source

```mox
package shop

class Order {
    String name
}
```

the artifact is exactly (2-space pretty JSON, deterministic key order):

```json
{
  "formatVersion": 1,
  "surface": "mox",
  "sourceHash": "sha256:06537d40d3cb9b566d340813965e61d635c78fd9b37a427e19394303e9b1a4b4",
  "generator": {
    "name": "pherolang",
    "version": "0.4.0"
  },
  "degraded": false,
  "spans": [
    { "start": 0, "end": 7, "class": "keyword", "modifiers": [] },
    { "start": 8, "end": 12, "class": "namespace", "modifiers": ["declaration"] },
    { "start": 14, "end": 19, "class": "keyword", "modifiers": [] },
    { "start": 20, "end": 25, "class": "type", "modifiers": ["declaration"] },
    { "start": 26, "end": 27, "class": "punctuation", "modifiers": [] },
    { "start": 32, "end": 36, "class": "property", "modifiers": ["declaration"] },
    { "start": 37, "end": 43, "class": "type", "modifiers": ["defaultLibrary"] },
    { "start": 44, "end": 45, "class": "punctuation", "modifiers": [] }
  ]
}
```

The source above ends with a newline; its hash covers exactly those bytes.

| Field | Type | Meaning |
|---|---|---|
| `formatVersion` | number | Compatibility gate. v1 is `1`; readers reject an absent or non-1 value |
| `surface` | string | Registry id (`mox`, `ifml`, `ddd`, `actor`, `evt`, `deploy`, `uc`, `cmmn`, `dmn`) |
| `sourceHash` | string | `sha256:<lowercase hex>` over the exact source bytes that were highlighted |
| `generator` | object | `{ "name": "pherolang", "version": "<crate version>" }`; informational, not a compatibility gate |
| `degraded` | boolean | `true` when the semantic pass was unavailable or incomplete; the artifact is still successful |
| `spans` | array | Ordered, non-overlapping span objects: `start`, `end`, `class`, `modifiers` |

### Rules

- **Casing.** Struct fields and modifier strings are camelCase
  (`sourceHash`, `defaultLibrary`); class strings are lowercase
  (`keyword`).
- **No source text.** Only `sourceHash` is emitted; the consumer already has
  the source. No path, file name, timestamp, host, environment, or absolute
  path appears.
- **Deterministic.** Key order is the order above; span order is by
  `start`; `modifiers` is the canonical modifier order with no duplicates.
  Serialization is 2-space pretty JSON. Two runs are byte-identical.
- **Half-open bytes.** `start`/`end` are byte offsets into the source,
  `[start, end)`, sorted and non-overlapping. Gaps are implicit.
- **Forward compatibility.** Unknown fields are ignored on read. New
  optional fields are additive and `#[serde(default)]`-friendly; new
  classes/modifiers are additive strings, but a forward-compatible consumer
  must skip a span it cannot name while the reference Rust model rejects an
  unknown value instead of guessing.
- **Versioning.** Additive changes keep `formatVersion: 1`. A re-purpose of
  a field, a unit change, or a removed/renamed field bumps the version and
  is a breaking change.
- **Empty input.** An empty source emits an empty `spans` array and
  `"degraded": false`.

### Versioning and compatibility

`formatVersion` is the compatibility gate, not a decoration. The policy is:

| Change | Version | Reader behaviour |
|---|---|---|
| New optional field, new class/modifier string, new surface id | stays `1` | Unknown fields are ignored; an unknown class/modifier is skipped by a forward-compatible consumer and rejected by the reference Rust model |
| Re-purposed field, unit change (bytes → UTF-16), removed or renamed field | bumps | The reference model rejects an absent, older, or newer version; there is no dual-accept window |
| Absent `formatVersion` | — | Rejected as version `0` (`HighlightError::UnsupportedFormatVersion`) |

The gate is exercised on committed bytes: `tests/highlight/invalid/format-version-2.json`
and `format-version-absent.json` must be rejected by
`HighlightArtifact::from_json`. The CLI does not read artifacts, so the
reader under test is the library contract every consumer is expected to keep.

The **site artifact** (`site/data/highlighting/spans.json`) is a separate
document with its own `formatVersion` (currently `1`). Its renderer rejects a
mismatched version with `data-phero-highlight="missing"`, which the site gate
turns into a merge failure. `generator.version` is provenance only — it names
the binary that produced the bytes and is never a compatibility boundary.

### Directory shape

Directory and multi-file input emit **one artifact per input file**, never a
single array artifact. The layout mirrors `pherolang build`:

- `<output>/<input path>.json` (JSON) or `<output>/<input path>.html`
  (HTML);
- `<input path>` is the path as given, with its directories preserved and
  root/prefix components dropped, so an absolute input never swallows the
  output directory;
- ordering is lexicographic by the expanded input path;
- the output directory is created as needed; nothing is written outside it.

`stdout` is **single-input only**. A single expanded input prints to stdout
unless `--output` names a file (written exactly there) or an existing
directory (the same mirrored path is used inside it). Multiple inputs
require `--output` to be a directory.

## HTML contract

The HTML renderer is a deterministic fragment for the site and editor
tooling, not a full document and not a theme:

```html
<pre class="pherolang-highlight"><code class="language-mox"><span class="hl-keyword">package</span> <span class="hl-namespace hl-declaration">shop</span></code></pre>
```

- Wrapper exactly: `<pre class="pherolang-highlight"><code
  class="language-<surface>">` … `</code></pre>`; no `<html>`/`<body>` and
  no added indentation.
- Each span is `<span class="hl-<class> hl-<kebab-modifier> …">` with the
  class first and modifiers in canonical order. Gaps are emitted as escaped
  source text.
- Escape the source exactly (`&`, `<`, `>`, and `"` in attributes); preserve
  newlines and whitespace. Never emit raw source.
- No inline styles, colours, theme variables, scripts, or data attributes.
  The renderer emits semantic class names only.
- The output is deterministic and diffable; one block per input.

The HTML format is a convenience over the JSON contract. If a consumer needs
the canonical data (hashes, degraded flag, exact classes), it reads JSON.

## The `pherolang highlight` command

```sh
pherolang highlight <file|dir|-> ... \
  [--format json|html] \
  [--mode strict|lenient] \
  [--surface <id>] \
  [--output <path>]
```

Examples:

```sh
pherolang highlight model.mox --format json
pherolang highlight model/ --format html --output target/highlight
printf 'class A { }' | pherolang highlight --surface mox --format json -
```

- Inputs are one or more files, a directory, or `-` for stdin. Directories
  expand exactly like `check`/`build` (supported surfaces only;
  formatter-golden `X.fmt.<ext>` files are skipped).
- `--format` defaults to `json`.
- `--mode` defaults to `strict` for files and directories and `lenient` for
  stdin and docs fences.
- `--surface` takes a registry id, an extension (with or without the dot),
  or an alias. It is required for stdin and may force one input file; it
  cannot be combined with a directory input or several files. Otherwise the
  surface is inferred from the extension.
- `--output` is a file for one input or a directory for multiple inputs;
  multiple inputs require a directory. See [Directory shape](#directory-shape).
- The command is offline: no network, and no filesystem access beyond the
  inputs and outputs.
- Exit codes:
  - `0` — success, including a `degraded` result;
  - `1` — an input could not be read, its extension does not name a
    supported surface, or the output could not be written;
  - `2` — usage error (missing or unknown `--surface`, `--surface` with a
    directory or several files, stdin combined with other inputs, multiple
    inputs without a directory output, conflicting flags, unknown option).

## Generated editor grammars (SH5)

The editor-facing compatibility layer is **generated**, never hand-written.
`phero_highlight::grammar` reads the same nine-surface metadata as the
highlighter and emits one TextMate grammar plus one language configuration per
surface. There is exactly one copy, at:

```text
site/packages/highlighting/
  package.json
  grammars/<surface>.tmLanguage.json
  language-configurations/<surface>.json
```

The package is reusable by the site and a future VS Code extension; both
consume this one copy. Publishing an extension is out of scope.

### Generate and check

```sh
pherolang grammar --out site/packages/highlighting
pherolang grammar --check site/packages/highlighting
```

`--out` writes the package (creating directories) and prints the file count.
`--check` validates the committed package byte for byte and exits `1` on a
missing, stale, or unexpected grammar/configuration file; a hand edit is a
failure, not a silently accepted copy. The command is offline and works from
`cargo run -p phero-cli -- …` as well as the released binary.

Regeneration is deterministic: no colour, timestamp, host, or absolute path
appears in a generated file, keys are emitted in a fixed order, two-space
pretty JSON with a trailing newline is used, and every grammar and
configuration starts with `formatVersion: 1` and the
`Generated by pherolang … do not edit.` header. The word lists come from
`phero_syntax::words` / `phero_ifml::words` through the registry, so a parser
keyword change is a regeneration, not a second list to update.

### What is generated

| Source (SH1 metadata) | TextMate scope |
|---|---|
| real lexer keywords (`metadata.keywords`) | `keyword.control.pherolang` |
| literals (`true`/`false`, `.ddd` ranking values) | `constant.language.pherolang` |
| builtin types (`metadata.builtin_types`) | `support.type.pherolang` |
| capitalized type-name heuristic | `entity.name.type.pherolang` |
| lowercase identifier | `variable.other.pherolang` |
| declaration name after a declaration word | the class scope (type/function/namespace/parameter/property/variable/constant) |
| escaped identifier (`^class`, Mox family) | type or variable by capitalization |
| annotation (`@name`) | `entity.name.function.decorator.pherolang` |
| strings and escapes | `string.quoted.double.pherolang`, `constant.character.escape.pherolang` |
| numbers | `constant.numeric.pherolang` |
| comments (and `///` / `/** */` docs) | `comment.pherolang`, `comment.block.documentation.pherolang` |
| punctuation / operators | `punctuation.pherolang`, `keyword.operator.pherolang` |

Declaration captures are anchored to the start of a line and use the
`metadata.declarations` mapping for the name's scope. Words that take a
reference or a clause rather than introduce a name (`import`, `inject`,
`connects`, `realizes`, `target`, `defaults`, …) are keyword-scoped but never
capture the following token as a declaration.

The language configuration carries the comment markers (`//`, and `/* */` for
the Mox family — `.ifml` has line comments only), brackets, auto-closing and
surrounding pairs (including `"` outside strings/comments), and a lexer-derived
`wordPattern`. Indentation rules are deliberately omitted: the formatter owns
layout, and an untested editor heuristic would drift from it.

### TextMate versus the compiler

TextMate grammars are regular expressions over one line; they cannot run the
parser. The generated grammar therefore matches the compiler's **lexical**
layer and necessarily diverges where the compiler uses parser state or the
semantic pass:

- **Contextual words are line-start only.** A contextual word (`id`, `service`,
  `decision`, `case`, `deployment`, …) is keyword-scoped when it starts a line
  and stays an identifier elsewhere. The compiler upgrades it in the parser's
  recognized positions, including pair positions (`inject decision`,
  `first … then`, `logic table`, `discretionary task`, …); the grammar does
  not guess at those pairs.
- **Declarations and references share a spelling.** A declaration name gets
  its metadata class through a line-start capture; the same word used as a
  reference falls back to the capitalized type-name heuristic or a variable.
  The compiler knows the difference; TextMate does not. Dotted names
  (`package a.b.c`, `base …`, `namespace …`) are one namespace span in the
  grammar, while the compiler scopes each segment separately and keeps the
  dots as punctuation.
- **`.ifml` structural words are lexical keywords everywhere.** The `.ifml`
  lexer has no keyword tokens; the SH1 registry classifies its curated
  structural words (`view`, `component`, `column`, `action`, `on`, `expr`, …)
  as keywords lexically. Property names such as `type`, `data`, `fields`, and
  `filter` are not structural words and stay ordinary identifiers in both the
  grammar and the lexer.
- **Semantic refinements are compiler-only.** The semantic pass may refine a
  lexical word into a declaration position: `.ddd` repository method names
  (`findById`, `findAll`, `save`, …) and search settings (`pagination`,
  `limit`, `max`, `cursor`) are line-start contextual keywords lexically but
  functions/properties in the artifact, and `.actor` `cedar` is an annotation.
  The grammar keeps the lexical keyword scope; the compiler artifact remains
  the source of truth.
- **Escaped keywords and reserved names.** `^class` is a name in the compiler;
  the grammar scopes the escaped identifier as a type/variable, but a plain
  keyword anywhere else remains a keyword.
- **No semantic overlays, colours, themes, or hover.** The grammar emits
  scope names only. The compiler-backed JSON/HTML stream remains the source of
  truth for the site and the LSP.

These divergences are measured, not asserted away: `check-grammars.mjs`
compares the Shiki token stream with the committed
`tests/highlight/json/support.*.json` artifacts, fails on a missed real keyword
or a keyword inside a comment/string/punctuation span, and prints the expected
contextual and semantic-refinement divergences as evidence.

### Validation

```sh
cargo test -p phero-highlight
cargo run -q -p phero-cli -- grammar --check site/packages/highlighting
pnpm -C site install --frozen-lockfile
node site/scripts/check-grammars.mjs
```

The Node check (also `pnpm -C site run check:grammars`):

1. asserts every surface in `site/data/surfaces.json` has a grammar and a
   language configuration with the expected shape;
2. loads all nine grammars in Shiki and tokenizes the corresponding
   `examples/support/support.*` file (an invalid regex or load failure is
   fatal);
3. pins representative scopes — `package`, `class`, `actor`, `event`,
   `decision_model`, `usecase`, `case`, `view`, `component`, `deployment`,
   plus builtin types, type names, literals, numbers, strings, punctuation,
   operators, annotations, and the declaration name each representative word
   introduces;
4. compares lexical scopes with the compiler-backed artifacts and reports the
   documented contextual and semantic-refinement divergence; and
5. fails on an absolute path, a missing file, or a malformed configuration.

The Rust side is the hand-edit guard: `crates/phero-highlight/tests/grammar.rs`
byte-compares the committed package, checks the vocabulary against the SH1
tables, pins the representative declaration scopes, and exercises the
missing/stale/unexpected paths of `check_grammars`.

Regenerate the committed package with the command above after a deliberate
metadata change, then read the diff. The generated files are the editor
contract.

## Static site integration (SH4)

Both origins — `pherolang.com` and `docs.pherolang.com` — consume **one
committed artifact and one renderer**. Neither app runs the compiler at build
time, and neither registers a second grammar.

### The artifact

`site/data/highlighting/spans.json` is generated by
`site/scripts/sync-highlight.mjs` and committed, like the rest of
`site/data/**`:

```json
{
  "formatVersion": 1,
  "generator": { "name": "pherolang", "version": "0.4.0" },
  "entries": {
    "<sha256(surface + \"\\0\" + source)>": {
      "surface": "mox",
      "sourceHash": "sha256:<hex over the source alone>",
      "degraded": false,
      "spans": [
        { "start": 0, "end": 7, "class": "keyword", "modifiers": [] }
      ]
    }
  }
}
```

- The **key** is `sha256(surface + "\0" + exact source bytes)`: the surface
  is part of the address, so identical bytes under `.mox` and `.ddd` cannot
  collide.
- `sourceHash` is the CLI artifact's own hash over the source alone; the
  renderer cross-checks it before using the spans.
- Entries are sorted by key. There are no paths, filenames, timestamps,
  colours, or environment data in the file. `formatVersion` is the site
  artifact's gate; unknown fields are ignored by readers.
- `degraded` is copied from the CLI. Docs fences are fragments and may be
  degraded; that is truthful, not a failure.

The inputs are exactly three buckets:

1. every Phero Lang fence in `docs/**/*.md`;
2. every `examples/support/support.*` model;
3. every excerpt declared in
   `site/packages/highlighting/excerpts.json` — the same manifest the
   marketing pages read, so a language-page excerpt hashes the bytes it
   actually renders, never the whole file.

Docs fences must equal Expressive Code's plaintext normalization (each line
right-trimmed, leading/trailing blank lines dropped). `sync-highlight` fails
with the file and line rather than storing an entry the docs transformer can
never find.

```sh
node site/scripts/sync-highlight.mjs           # regenerate
node site/scripts/sync-highlight.mjs --check   # compare without writing
```

The CI `Site` workflow runs the same script in its freshness and nightly drift
jobs and fails on a `git diff` under `site/data/`.

### Marketing app

`site/packages/ui/src/CodeBlock.astro` keeps the existing figure, caption,
`data-runnable` contract, `tabindex="0"`, overflow handling, and
`language-<surface>` class. For a Phero surface it looks up the span entry for
the exact `code` bytes and renders the compiler's classes; every other
language stays plaintext. A missing entry renders plaintext **and** adds
`data-phero-highlight="missing"`, which the site gate fails on — production
never silently regresses.

### Docs app — the chosen integration

Starlight renders Markdown fences through Expressive Code, which normally owns
tokenization. The chosen path is **Option D**: an Expressive Code plugin at
`site/phero-docs/ec.config.mjs` (`site/packages/highlighting/src/ec-plugin.mjs`)
that runs at `postprocessAnalyzedCode` and `postprocessRenderedLine`.

The plugin only splits the text nodes Expressive Code already rendered and
wraps the compiler's byte ranges in `hl-*` spans. Expressive Code keeps
ownership of:

- the frame, copy button and its JavaScript module,
- gutters and line numbers,
- multi-theme switching and the theme CSS,
- existing text-marker annotations,
- the accessible structure of the block.

Nothing is re-rendered and no JavaScript is added. A missing/incomplete
artifact leaves the block as plaintext and adds
`data-phero-highlight="missing"`; the gate fails. This path lost no UX, so the
component-override fallback (Option B) was not needed.

The plugin receives Expressive Code's normalized plaintext; that is why the
docs fence normalization rule above is part of the artifact contract. The
generated TextMate grammars (SH5) remain the editor/fallback grammar; the site
does not register them, so there is no second highlighting path in the browser.

### Release binary status

The latest published release, **v0.4.0, is the source of the committed site
data**: it contains `pherolang highlight` and can check the DD9 examples on this
tree. `site/data/highlighting/spans.json` was regenerated with the released
asset and `git diff --exit-code site/data` was empty, so SH8's release
acceptance is satisfied.

The site does not silently use the wrong binary:

1. `PHEROLANG_BIN`, when set, must satisfy the requested capability;
2. `site/.bin/pherolang` is used only if it can check
   `examples/support/support.ddd` and, for `sync-highlight`, provides
   `pherolang highlight`;
3. `pherolang` on `PATH` follows the same rule;
4. otherwise the tooling builds the CLI from the checkout
   (`cargo build -q -p phero-cli`, then `target/debug/pherolang`).

The same `resolveSiteBinary` governs `sync-model`, `sync-highlight`, and the
command executor the gate runs, so one binary produces all site data. Step 4 is
now an **offline/development fallback** for a checkout that has not fetched a
release, not how the committed data is produced: `scripts/fetch-pherolang.mjs`
pins `0.4.0`, which is published, and an explicit pin never falls back to
another release. The `Site` workflow installs Rust so the fallback can still run
without a download, exports the resolved binary, and prints which one it used
every run.

Two further release gates make the window honest:

- the release workflow runs the built binary and asserts `pherolang highlight`
  emits `formatVersion: 1` for `mox`, and that `grammar --out`/`--check`
  round-trip — so a release cannot ship without the site's contract;
- the `deploy` job requires the latest release version to equal the workspace
  version, so production never advertises a download that does not exist.

After v0.4.0 is published: `node site/scripts/fetch-pherolang.mjs`,
`node site/scripts/sync-model.mjs`, and `node site/scripts/sync-highlight.mjs`
run against the released asset, and the committed data is expected to stay
byte-identical. v0.4.0 was published on 2026-11-17 from `ba2b267`; the executed
sequence and its empty diff are recorded in
[RELEASE-0.4.0.md](RELEASE-0.4.0.md).

### Theme tokens

The artifact carries no colours. `site/packages/highlighting/src/highlight.css`
maps the stable `hl-*` classes to `--code-*` variables in
`site/packages/tokens/src/tokens.css`, shared by both apps:

- `--code-bg` (`#FFFFFF` light / `#1C2028` dark) is the measured code-block
  surface;
- one `--code-<class>` value per class, light and dark, plus modifier cues
  (bold declaration, italic readonly/documentation, strikethrough deprecated);
- `prefers-color-scheme` and Starlight's `data-theme` switch both select the
  same measured tokens, so there is no flash of unhighlighted content;
- every code colour is measured by `site/scripts/gate/contrast.mjs`, and axe
  covers representative pages in light and dark modes.

### Site gate

`site/scripts/gate/highlighting.mjs` is part of `node site/scripts/gate.mjs`:

- every Phero block in both built apps contains `hl-*` classes;
- no raw `class="language-<surface>"` block remains in marketing output;
- every docs fence language is Phero or explicitly exempt
  (`text`, `markdown`, `sh`, `rust`, `json`, `jsonc`, `html`, …);
- every source has an artifact entry, and no stale entry remains;
- the artifact is format-versioned, path-free, timestamp-free and colour-free;
- no `<script>` is emitted inside a code block (the client-JS budget is
  unchanged);
- contrast and a11y cover the code tokens in both modes.

`site/scripts/sync-highlight.mjs` is also wired into the site gate's
`freshness` check and the `Site` workflow; a stale artifact is a merge failure.

## Interactive hover surface (SH7)

SH7 asked for hover documentation on the public site. The accepted decision is
**Option A**: a static, zero-JavaScript reference surface at `/demo/hover`,
not a browser IDE. The reasoning, the measured and estimated costs, and the
deferred editor work live in
[ADR 0002](adr/0002-static-hover-reference-panels.md); this section records
only how the surface fits the highlighting contract.

### Data flow

The page adds one authored layer and no new compiler output:

- `site/data/highlighting/spans.json` — the SH4 artifact — remains the only
  span source. A symbol is identified by an existing span, never by a second
  tokenizer.
- `site/packages/highlighting/hover.json` is the authored index. Each entry
  names a compiler graph node id from `site/data/graph.json`, the span class
  and optional `declaration` modifier that identify the token, and a
  signature that must appear (whitespace-normalised) in the excerpt.
- The documentation link is derived from the node file's surface through
  `site/data/surfaces.json` and `site/data/docs-manifest.json`. A missing
  page is an error, not a guessed URL.
- `site/packages/highlighting/src/hover.mjs` resolves and validates all of
  that at build time. `site/phero-web/src/components/HoverCode.astro` renders
  one example, and `site/phero-web/src/pages/demo/hover.astro` is the route.

The prototype covers two examples and six symbols: a `.mox` class with its
two refund operations, and a `.ddd` service, its operation, and the
capability that gates it.

SH7 uses the SH4 span stream and the same class/modifier vocabulary as SH6,
but **not** SH6's LSP transport. There is no language server, worker, or
WebSocket in the page; SH6 remains the editor path.

### Zero client JavaScript

The built page emits no `<script>` element. The floating card is painted by
CSS `:has()` when a symbol is hovered or focused, and it is a visual duplicate
of a permanent reference entry that is always visible below the code. The
permanent panel carries the real documentation link and the full signature,
kind, and summary, so no information is hover-only and a browser without
`:has()` loses the preview but keeps every fact.

The symbol is an ordinary anchor to its panel entry. Enter moves focus to that
entry (`tabindex="-1"`), and the documentation link is next in tab order. The
card is `aria-hidden` and contains no focusable content, so it cannot create a
focus trap. No animation or transition is introduced; the global
`prefers-reduced-motion` policy is unchanged.

### Failure behaviour

A missing or unreadable index (invalid JSON), an unresolved graph node, a
missing span, a signature absent from the excerpt, or a node with no
documentation page makes that example fall back to the plain highlighted
block and sets `data-hover-fallback`. The page still builds and the other
example still renders. The hover gate fails on the marker, so the prototype
cannot vanish silently.

### Measured budget

Measured on this tree; gzip uses Node's zlib at level 9.

| Surface | Raw | Gzip |
|---|---|---|
| Client JavaScript | 0 bytes (no `<script>` emitted) | 0 bytes |
| `site/packages/highlighting/src/hover.css` | 4,133 bytes | 1,235 bytes (gate budget 8 KiB) |
| `site/packages/highlighting/hover.json` | 3,683 bytes | 1,093 bytes, build-time only |
| `site/phero-web/dist/client/demo/hover/index.html` | 54,265 bytes | 8,440 bytes |

The page is one more prerendered asset on the existing Workers static-assets
deployment — no new binding, KV, Durable Object, container, secret, or runtime
process. The marketing build now emits 20 HTML pages against a floor of 19.

### Validation

`site/scripts/gate/hover.mjs` is part of the local
`node site/scripts/gate.mjs` run. It validates `hover.json` against the
committed artifact, graph, surfaces table, and docs manifest; asserts the
built page has no `<script>` and no fallback marker; enforces the gzip CSS
budget; and drives Playwright through hover, focus, and Enter, with axe on the
focused state and a reduced-motion pass. The `a11y` check also covers the
route in light and dark.

The browser checks are **local only** by explicit choice. CI's `Site verify`
job runs `pnpm -C site test`, which includes the pure committed-index test in
`site/scripts/test/hover.test.mjs`; it does not run the interactive gate.

### Deferred

The editor shape (Monaco or CodeMirror plus an LSP client and a WASM or
Worker/WebSocket transport) is deferred, along with editing, completion,
diagnostics, multi-file projects, and symbol coverage beyond these two
examples. See [ADR 0002](adr/0002-static-hover-reference-panels.md) for the
cost comparison and the alternatives considered.

## CSS and themes

The highlighter emits semantics; the site owns presentation.

- Style the stable class names (`.hl-keyword`, `.hl-type`,
  `.hl-default-library`, …). They are part of the contract; renaming one is
  a breaking change.
- Colour, contrast, typography, and light/dark belong to the site's token
  layer and stylesheets. No colour is emitted or hardcoded by the
  highlighter.
- Both apps import the same `site/packages/highlighting/src/highlight.css`;
  it maps `hl-*` to the measured `--code-*` variables in
  `site/packages/tokens/src/tokens.css` and contains no literals.
- Theme selectors may compose class and modifier, but must not depend on
  source element names or inline styles. Modifiers add a non-colour cue
  (weight, italic, underline, strike) rather than a second colour.
- Contrast is measured in both light and dark modes by the site's
  accessibility gate, not by this crate.

## Quality gates

The highlighting slice is gated like the rest of the compiler:

- **Golden JSON** for every `examples/support/support.*` surface, under
  `tests/highlight/`.
- **Golden HTML** for a representative fixture per surface.
- **Checked corpus**: `tests/highlight/corpus/` covers every surface with
  valid, truncated, and parse-error inputs, plus Unicode/emoji/combining,
  CRLF, escapes, doc comments, contextual words in real and ordinary
  positions, and `.ifml` words that look like other surfaces' keywords. The
  compact class summary is `tests/highlight/summary/corpus.json`; a
  representative subset is byte-pinned under
  `tests/highlight/json/corpus.*.json`. A surface without a corpus case fails
  by name.
- **Docs-fence corpus**: every Phero Lang fence in `docs/**/*.md` is
  highlighted and summarized in `tests/highlight/summary/docs-fences.json`;
  a surface with no fence fails by name, and a changed fence is a visible
  golden diff.
- **Span invariants**: sorted, non-overlapping, in bounds, no empty spans,
  no split comments/strings.
- **Unicode/UTF-16**: emoji, combining characters, CRLF, and non-ASCII
  identifiers produce correct byte spans and UTF-16 conversion; the source
  hash covers the exact bytes.
- **Determinism**: a second run is byte-identical, in stdout and directory
  mode.
- **Performance budget**: one lex and one parse per input; the support
  corpus plus the docs-fence corpus completes within the coarse threshold
  recorded with the test (a CI budget, not a microbenchmark).
- **Drift tests**: every token variant is classified or explicitly ignored;
  every word-table entry is registered; every logos keyword is classified;
  all nine surfaces have a registry entry and a corpus case; contextual words
  do not leak between surfaces; `formatVersion` rejection (including the
  committed invalid fixtures) and "no absolute paths" are pinned.
- **CLI contract**: black-box tests cover files, directories, stdin, JSON,
  HTML, `--mode`, `--surface` id/extension/alias, `--output` file/directory,
  exit codes `0`/`1`/`2`, and determinism.
- **Generated editor grammars**: every surface has a TextMate grammar and a
  language configuration; the committed package is byte-identical to the
  generator; every grammar loads in Shiki and tokenizes its support example;
  the representative scopes are pinned; and the compiler-vs-TextMate
  divergence is measured. Regenerate with
  `pherolang grammar --out site/packages/highlighting` and validate with
  `node site/scripts/check-grammars.mjs`.
- **No hand-maintained site list**: a keyword added to a parser table must
  never require editing `site/` or `phero-highlight`.
- **Zero-JS pages**: every built marketing page except the documented graph
  island on `/demo` references no executable script and contains no inline
  executable script; the island's gzipped bytes stay under the 12 KB budget.
  Gate: `site/scripts/gate/budget.mjs`.
- **Release contract**: the release workflow runs the built binary and
  asserts `pherolang highlight` emits `formatVersion: 1` and that
  `grammar --out`/`--check` round-trip; production deploy waits for the
  released version to match the workspace version.
- **Static site artifact**: `site/data/highlighting/spans.json` covers every
  Phero docs fence, every `examples/support/support.*` model, and every
  declared excerpt; every built Phero block in both apps carries `hl-*`
  classes; the artifact is fresh, path-free and colour-free; code-token
  contrast passes in light and dark; and no client JS is added by this
  pipeline. Gate: `site/scripts/gate/highlighting.mjs`.
- **Static hover surface**: every `hover.json` entry resolves to exactly one
  existing span and one committed graph node, its signature appears in the
  excerpt, its docs page exists, and every example annotates both a
  class/type and a capability/operation; the built `/demo/hover` page emits
  no `<script>`, has no `data-hover-fallback` marker, keeps the hover CSS
  under 8 KiB gzip, and passes the hover/focus/Enter, axe, and reduced-motion
  checks. Gate: `site/scripts/gate/hover.mjs`, run by
  `node site/scripts/gate.mjs` — the interactive checks are **local only**.
- **Pure hover index test**: `site/scripts/test/hover.test.mjs` validates the
  committed index and the annotated HTML renderer without a browser, and is
  part of `pnpm -C site test` (the CI `Site verify` job), so a broken index
  fails CI even though the interactive gate does not run there.

Regenerate the goldens with:

```sh
PHERO_UPDATE_FIXTURES=1 cargo test -p phero-cli --test cli highlight
PHERO_UPDATE_FIXTURES=1 cargo test -p phero-highlight --test corpus
cargo run -q -p phero-cli -- grammar --out site/packages/highlighting
node site/scripts/sync-highlight.mjs
```

`scripts/ci-local.sh` also runs `grammar --check` in its format step, so a
hand-edited generated grammar fails the Rust gate without Node.

## Troubleshooting

**A Phero block renders plaintext / the gate says `data-phero-highlight="missing"`.**
The block's exact bytes have no artifact entry. Regenerate with
`node site/scripts/sync-highlight.mjs` and commit the diff. A docs fence that
renders differently from its source usually has trailing whitespace or a
leading/trailing blank line: Expressive Code normalizes those, and the script
fails with the file and line rather than storing an entry the transformer can
never find.

**A golden changed and I did not touch the highlighter.**
A parser, word-table, or docs change moved the span stream. Regenerate with
the commands above and read the diff — the goldens are the spec. Never edit a
`tests/highlight/json/**`, `tests/highlight/summary/**`,
`site/data/**`, or `site/packages/highlighting/**` file by hand.

**`committed grammar package is stale` / `grammar --check` fails.**
A generated grammar or language configuration was hand-edited, or the registry
changed without regeneration. Run
`cargo run -q -p phero-cli -- grammar --out site/packages/highlighting`, then
`cargo run -q -p phero-cli -- grammar --check site/packages/highlighting`.

**`node site/scripts/check-grammars.mjs` cannot load a grammar.**
Reinstall the site workspace (`pnpm -C site install --frozen-lockfile`); the
script needs Shiki. It also fails on a malformed regex or a missing file, not
just a bad scope.

**The site tooling says the release cannot check the tree.**
v0.3.0 predates both `pherolang highlight` and the DD9 examples. The resolver
rejects it and builds this checkout; that is the documented source-build
exception, not an error. Set `PHEROLANG_BIN` to a build you trust, or wait for
v0.4.0 ([RELEASE-0.4.0.md](RELEASE-0.4.0.md)).

**`sync-highlight` reports `formatVersion` or `sourceHash` mismatch.**
The binary and the committed artifact disagree. Regenerate with the same
binary the gate resolves; do not patch the JSON. A site artifact version
mismatch is rejected by the renderer and is a hard gate failure.

**Punctuation or lexical errors have no LSP token.**
By design: `punctuation` and `error` have no standard LSP type. Punctuation is
the editor grammar's job (SH5); lexical errors are diagnostics, not colours.

**Contrast or axe fails only in dark mode.**
The dark pass asserts the scheme applied before analysis
(`html[data-theme="dark"]` or `prefers-color-scheme: dark`). A code token that
was added without a measured `--code-*` pair fails `contrast.mjs`; add the
pair to `site/packages/tokens/contrast.json` and the token to
`site/packages/tokens/src/tokens.css`.

## Performance

The engine performs **one lex and one parse per input**; it never reparses per
token and never allocates a second copy of the source. The semantic pass is a
walk over the spanned AST. The site does no highlighting at request or build
time — it looks up a content-addressed span entry by
`sha256(surface + "\0" + source)`.

The checked budget is deliberately coarse: `documentation_fences_highlight_within_the_performance_budget`
runs every support example and every docs fence and fails above **30 seconds
in a debug test build** on shared CI. That is a regression guard, not a
microbenchmark; on a current Linux x86_64 machine the same pass completes in
well under a second in a release build and in a few seconds in debug. Measure
locally with:

```sh
/usr/bin/time -f '%e s, %M KB' cargo test -p phero-highlight --test engine \
  documentation_fences_highlight_within_the_performance_budget -- --exact
```

Hardware, toolchain, and the binary that generated the site data are recorded
in `site/data/evidence.json` and `site/data/highlighting/spans.json`'s
`generator` stamp. A separate scheduled benchmark is a follow-up, not a gate.

surface (Option A); the browser editor (Option B) is deferred. SH8's release
acceptance is consistent with the release state above: **v0.4.0 is prepared
but not published in this slice**, so the site data is source-built until the
operator tags it.

JavaScript on static pages.
